# 80km/h 조건의 인식 연구: 모델 후보와 검증 기준

> **과거 실험·연구/인터페이스 참고 문서.** 아래 수치와 진행 표현은 문서 작성 당시의 범위입니다. 현재 완료 결과와 취소/미검증 항목은 [RESULTS](RESULTS.md), 재현 절차는 [REPRODUCIBILITY](REPRODUCIBILITY.md), 운용 한계는 [LIMITATIONS](LIMITATIONS.md)를 우선 확인하십시오. 예제 명령은 설치 시 실행되지 않으며 학습·다운로드·서비스·제어의 새 실행을 뜻하지 않습니다. 로컬 경로는 이 공개본에서 프로젝트 상대 예제로 바꿨습니다.

확인일: 2026-10-21. 이 문서는 **녹화 영상·시뮬레이션에서 평가할 후보 선정안**이다. 새 모델 설치, 가중치 다운로드, GPU 학습, 차량 운행은 이 조사에서 수행하지 않았다. 현재 TinyUNet 도로 분할과 joint waypoint 모델을 80km/h 운행에 사용할 수 있다는 의미가 아니다.

**후보의 단독 GPU 벤치마크 결과는 아직 없다.** 다른 학습 작업과 GPU 자원을 공유하는 동안 얻은 시간을 후보의 독립 처리 지연으로 사용하지 않는다. 아래 수치는 출처를 밝힌 공식 공개 수치, 광학 계산 또는 목표 예산이며 이 장치에서 실행한 측정치가 아니다.

현재 결론은 **학습에는 RTX3080 Laptop의 16GB를 활용하고, n/s/m/l/x 전체를 배포용4GB·8GB 조건에서 비교한다**이다. A/B/C는 초기 비교 기준이며 s 또는 n이 하드웨어의 최대 모델이라는 뜻은 아니다. 자체 거리별 재현율·오검출·전체 처리 지연을 측정하기 전에는 어느 후보도 최종 선정하지 않는다. 카메라 8대나 VRAM 8GB라는 조건만으로 무사고를 보장할 수 없다.

## 설치 상태와 실제 지원 범위

`.\.venv`의 패키지 메타데이터와 설치 파일을 읽어서 확인했다.

| 항목 | 확인 결과 |
|---|---|
| PyTorch | 2.9.1+cu126 |
| torchvision | 0.24.1+cu126 |
| Ultralytics | 8.4.182 |
| YOLO26 n/s/m/l/x | 설치된 `cfg/models/26/yolo26.yaml`에 다섯 scale 및 `end2end: True` 존재 |
| 추적기 | 설치된 `bytetrack.yaml`, `botsort.yaml` 등 설정 존재 |
| YOLO26 semantic/depth | 모델 YAML이 설치되어 있음. 이 프로젝트에 연결·검증되었다는 뜻은 아님 |
| Transformers, ONNX Runtime, TensorRT | 해당 가상환경의 패키지 메타데이터에서 발견되지 않음 |
| PIDNet/SegFormer | torchvision 기본 segmentation 구현에 없음. 별도 검증한 구현/어댑터가 필요 |

라이브러리가 모델 구조를 지원하는 것과 학습된 체크포인트가 준비된 것은 다르다. `YOLO('yolo26s.pt')`처럼 파일 이름만 넣으면 자동 다운로드할 수 있으므로, 향후 실행은 검증한 로컬 가중치 경로와 출처 해시를 사용한다.

## 학습 자원과 배포 조건은 별도

학습은 **RTX3080 Laptop GPU 16GB·RAM32GB**, 탑재 추론은 **실제GPU VRAM4GB 또는8GB·RAM16GB**를 기준으로 한다. 배포 메모리 조건 때문에 학습까지4GB·8GB로 제한하지 않는다. 현재 joint 학습 함수도 `runtime.torch_allocator_cap_gib`를 학습에 적용하지 않는다. AMP와 배치 크기를 실제 학습 처리량·메모리에 맞춰 조정하되 다른 작업·운영체제의 여유를 남긴다. 메모리를 가득 채우는 것 자체가 목적은 아니다.

가장 큰 기본 검출 모델인 YOLO26x도 직접 배포 후보로 포함한다. 공식 fused 파라미터 약55.7M의 FP16 **가중치만** 계산하면 약111.4MB(106.2MiB)다. 실제 VRAM에는 중간 활성값, 연산 작업공간, 입력, CUDA 컨텍스트, 다른 모델 등이 더해진다. 학습에는 gradient·optimizer·EMA 같은 상태도 추가된다. 따라서4GB라는 수치만으로 x를 배제하거나 실행 가능하다고 확정하지 않는다.

| 모델 | 공식 fused 파라미터 | FP16 가중치만, 근사 MiB | 공식 T4 TensorRT10 단일 영상 지연 |
|---|---:|---:|---:|
| YOLO26n | 2.4M | 4.6 | 1.7ms |
| YOLO26s | 9.5M | 18.1 | 2.5ms |
| YOLO26m | 20.4M | 38.9 | 4.7ms |
| YOLO26l | 24.8M | 47.3 | 6.2ms |
| YOLO26x | 55.7M | 106.2 | 11.8ms |

위 지연은 입력640·NMS-free head의 공식 측정이며 MSI나 현재RTX3080 실측이 아니다. 단순히 단일 영상 시간을8배 하면 s는20ms, x는94.4ms다. 이는 순차 처리의 비용을 설명하는 산술 예시이며 실제8카메라 벤치마크가 아니다. 8카메라 각각30Hz면 초당240개 영상 처리가 필요하고, 공유 순차 검출기에 허용되는 평균 시간은 영상당약4.17ms보다 짧아야 다른 처리의 여유가 생긴다. 배치·파이프라이닝에 따라 결과는 달라지지만 영상 수에 따른 총 연산은 없어지지 않는다. [YOLO26 공식 조건·표](https://docs.ultralytics.com/models/yolo26/)

큰 모델을 먼저 학습한 뒤 동일한 모델을 FP16/TensorRT로 직접 배포하는 실험과, 큰 모델을 교사로 사용해 작은 모델을 별도 학습하는 증류 실험을 구분한다. x 체크포인트를 n/s로 이름만 바꿔 사용할 수 없다. 증류·INT8 양자화는 정확도 유지가 보장되지 않아 작은 장애물·야간·원거리 자료로 다시 평가한다. 현재 프로젝트의 증류 연결 및 TensorRT 엔진은 구현·생성되지 않았다. [Ultralytics export 공식 문서](https://docs.ultralytics.com/modes/export/)

정의는 `configs/model_scale_experiment.json`에 있다. 이는 실험 명세이며 학습 실행기가 아니다. `scripts/benchmark_detector_candidates.py`는 n/s/m/l/x를 모두 받아 무작위 모델의 구조 비용을 검사한다. 동작 환경의 GPU 자체가 없으므로 메모리 제한을 건 RTX3080 결과를 MSI의 성능으로 표시하지 않는다.

## 초기 기준 구성과 확장 후보

다음 해상도는 실험 시작점이며 성능이 확인된 운용 사양이 아니다. H×W로 적은 semantic 해상도와 검출기의 `imgsz`를 구분한다. 원본 종횡비를 보존하는 resize/letterbox, 렌즈 보정, 좌표 복원은 모델별로 검증한다.

| 후보 | 목표 장치 | 객체 검출 | 도로·경계 분할 | 선택 이유 및 평가할 위험 |
|---|---|---|---|---|
| **A: 우선 비교** | 전용 VRAM 8GB, RAM 16GB | **YOLO26s**: 전방 `imgsz=960`와 640을 비교, 측후방 640부터 | **PIDNet-S**: 전방 512×1024부터; 원본 비율이 다르면 보존하는 크기로 변경 | 검출 모델 용량과 도로 경계 보존을 함께 늘린다. 전방 960의 작은 객체 재현율 이득과 8뷰 지연을 반드시 같이 측정 |
| **B: 4GB 비교군** | 기존 MSI 4GB, RAM 16GB | **YOLO26n**, 우선 640 | **PIDNet-S**: 384×768과 512×1024 비교 | 모델은 방향별로 복제하지 않고 공유 인스턴스로 순차 처리. 축소가 정확도·거리별 재현율을 낮추면 채택하지 않음 |
| **C: 분할 구조 비교군** | 전용 VRAM 8GB | A와 같은 YOLO26s 설정 | **SegFormer-B0 Cityscapes**: 512×1024 시작, 필요시 1024 기준 비교 | 주변 문맥과 경계 오류가 PIDNet보다 나아지는지 비교. 파라미터가 적다는 이유만으로 속도가 빠르다고 판단하지 않음 |
| **D/E/F: 큰 검출기 직접 배포** | 4GB·8GB에서 각각 비교 | **YOLO26m/l/x**, 640·960 | 분할기는 PIDNet-S로 고정해 검출기 변경 효과 분리 | 모델 크기로 미리 배제하지 않고 실제 정확도·전체 지연·메모리를 비교 |

PIDNet의 경계 분기는 **도로를 포함한 semantic 영역의 경계**를 보존하기 위한 구조다. 이를 차선 표시별 인식 모델로 취급하지 않는다. 차선·정지선·횡단보도 등 표시의 구분과 차선 연결 관계가 필요하면 별도의 head 또는 분류 가능한 라벨, 평가 기준을 마련하고 검증해야 한다. [PIDNet 원 논문](https://arxiv.org/html/2206.02066v2)

세 후보의 공통 실험 구성으로 **명시적으로 선택한 ByteTrack**을 카메라별 **2D 영상 ID 유지**에 사용할 예정이다. 이것만으로 3D 위치·거리, 카메라 간 동일 객체 연결이나 미터 단위 속도가 계산되지는 않는다. 후속 다중 카메라 융합에서는 카메라 보정, 촬영 시각, 차속·회전율, 동일 객체 대응, 거리 불확실성을 별도로 처리해야 한다. 기본 tracker 이름은 라이브러리 버전에 따라 바뀔 수 있으므로 설정에 `bytetrack.yaml`을 고정한다. [Ultralytics 추적기 공식 문서](https://docs.ultralytics.com/modes/track/)

거리 추정은 먼저 보정된 전방 스테레오/다중 시점과 실제 거리 정답으로 검증한다. 단안 깊이는 추가 실험으로만 사용하며, 현재 설치 구조에 있는 **YOLO26n-depth**를 전방 한 뷰에서 비교할 수 있다. 공식 수치의 주요 평가 대상은 실내 NYU Depth V2이고 정답을 이용한 scale 정렬·TTA 조건이 포함되므로, 이를 80m 실외 절대 거리 정확도로 바꾸어 해석할 수 없다. 이 추가 head는 A/B/C 모두에서 별도 ablation으로 보고하며, 처음부터 8뷰 전체에 실행한다고 가정하지 않는다. [공식 depth 조건](https://docs.ultralytics.com/tasks/depth/)

## 공식 수치를 해석할 때의 구분

| 모델 | 공개된 대표 수치 | 그 수치가 측정된 조건 |
|---|---|---|
| YOLO26n / s | COCO mAP50–95 **40.9 / 48.6**; end-to-end head **40.1 / 47.8** | 입력640. 공개 T4 TensorRT10 지연 **1.7 / 2.5ms**는 해당 GPU·추론 조건 수치이며 카메라 취득과 전체 시스템 지연이 아님 |
| PIDNet-S | Cityscapes test mIoU **78.6%**, **93.2FPS**, 7.6M parameters | 원 논문의 **RTX 3090**, 2048×1024 조건. GTX1650 Max-Q 또는 일반 8GB GPU 수치가 아님 |
| SegFormer-B0 | 작은 transformer semantic 후보; NVIDIA 계정의 Cityscapes 체크포인트 제공 | 체크포인트는 1024×1024 fine-tuning. 해당 해상도 이름이나 적은 파라미터 수가 MSI 처리량을 보장하지 않음 |

출처: [YOLO26 공식 표](https://docs.ultralytics.com/models/yolo26/), [PIDNet 공식 저장소](https://github.com/XuJiacong/PIDNet), [PIDNet 원 논문의 장치·해상도 조건](https://arxiv.org/html/2206.02066v2), [NVIDIA SegFormer 저장소](https://github.com/NVlabs/SegFormer), [NVIDIA Cityscapes B0 체크포인트](https://huggingface.co/nvidia/segformer-b0-finetuned-cityscapes-1024-1024).

YOLO 공식 표의 파라미터 수는 fusion 및 사용하지 않는 학습 head 제거 후 기준이다. 로컬 YAML의 전체 학습 구조가 n=2,572,280 / s=10,009,784 parameters로 표시되어도 공식 추론 표와 곧바로 모순되는 것은 아니다. NMS-free detector의 end-to-end라는 표현은 **검출 후처리 방식**을 뜻하며, 자율주행 전체가 완성되었다는 뜻이 아니다. [공식 모델 설명과 계수 조건](https://docs.ultralytics.com/models/yolo26/)

기존 SegFormer 공식 저장소의 설치 예시는 오래된 PyTorch/MMCV 조합이다. 현재 가상환경을 그 버전으로 낮추지 않고, 별도 환경 또는 검증한 최신 어댑터에서 확인해야 한다. PIDNet 저장소는 기존 가중치 링크 일부의 장애를 공지하므로 실제 취득 때 공식 안내의 대체 링크와 해시를 기록한다. Ultralytics는 AGPL/Enterprise 조건, PIDNet 코드는 MIT, SegFormer 공식 자료는 연구·평가 중심의 별도 조건이 있으므로 향후 배포 범위에 맞춰 확인한다. [PIDNet 저장소](https://github.com/XuJiacong/PIDNet), [SegFormer 설치·사용 조건](https://github.com/NVlabs/SegFormer)

## 80m 앞의 15cm 장애물은 몇 픽셀인가

다음은 왜곡을 보정한 pinhole 카메라, 정사각 픽셀, 광축 부근의 정면 물체, 유효 영상 폭 W를 가정한 근사 계산이다. 실제 보정값 `fy`가 있으면 그것을 사용한다.

```text
f_pixels ≈ W / (2 × tan(horizontal_FOV / 2))
object_height_pixels ≈ f_pixels × object_height_metres / distance_metres
```

이는 투영 기하 계산이지 검출 성공률이 아니다. resize 이후 카메라 행렬도 같은 비율로 변환해야 한다. [OpenCV 카메라 투영·보정 공식 문서](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html)

| 수평 화각 | 유효 폭640에서 15cm / 80m | 유효 폭960에서 15cm / 80m |
|---|---:|---:|
| 90° | **0.60px** | **0.90px** |
| 60° | **1.04px** | **1.56px** |
| 30° | **2.24px** | **3.36px** |

따라서 960 입력으로 바꾸는 것만으로 80m 작은 낙하물을 안정적으로 구분한다고 말할 수 없다. 더 좁은 화각은 먼 물체를 크게 보여주지만 주변 시야를 줄인다. 전방 원거리 카메라와 주변 광각 카메라의 겹침을 실제로 측정해야 한다. 원본 고해상도에서 관심 영역을 잘라 쓰는 방식은 검토할 수 있지만, 이미 1픽셀로 줄인 영상을 확대해도 사라진 정보를 복원하지 못한다. 분할 결과를 원본 크기로 보간하는 것도 같은 한계가 있다.

COCO의 80개 범주에는 보행자·차량 같은 대상이 있지만, 임의의 작은 낙하물·파편을 포괄하는 보장이 없다. `car/person` 재현율과 별개로 **미등록 장애물, 가려진 물체, 낮은 대비, 역광·비·안개** 자료를 평가해야 한다. 도로로 분할되었다고 비어 있다고 판단하지 않는다. [실제 COCO 범주 정의](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/datasets/coco.yaml)

## 처리 지연 설계

80km/h는 약 **22.22m/s**다. 관측이 50ms 늦으면 1.11m, 100ms면 2.22m, 150ms면 3.33m를 이동한다. 이 계산에는 제동 거리와 제어기·액추에이터 지연이 포함되지 않는다. 인식 100ms를 만족하더라도 80km/h 안전 운행이 증명되지는 않는다.

1. 전방 원거리 검출, 주변 객체, 도로 경계, 추적·기하 융합을 분리해 각각의 p50/p95/p99/최대 시간을 기록한다. CUDA는 동기화하여 측정하고 CPU 전처리·복사 시간을 제외하지 않는다.
2. **노출 시각 → 결과 소비 시각**을 측정한다. 호스트의 수신 시각만 사용하는 현재 카메라 소스는 노출·USB 버퍼 지연을 확인하지 못한다. 카메라별 노출 시각, 프레임 ID, drop, 동기 오차와 가장 오래된 입력의 나이를 기록한다.
3. 예를 들어 100ms라는 인식 연구 예산을 먼저 정한다면, 취득25 + 전처리10 + 모델40 + 추적·융합10 + 판단5 + 여유10ms로 분해해 **각 예산의 실현 가능성을 실제 장치에서 측정**한다. 이는 목표 배분 예시이며 검증된 제한값이나 운행 허용 기준이 아니다.
4. 8대 모든 카메라에 두 큰 모델을 각각 복제하지 않는다. detector 1개와 semantic 모델 1개를 공유하고 batch1 또는 작은 묶음부터 측정한다. FP16·TensorRT·INT8는 각각 정확도 재평가가 필요한 별도 후보다. 현재 TensorRT는 설치되지 않았다.
5. 전방 빈도를 높이고 측후방 빈도를 낮추는 스케줄은 향후 2D 인식 실험에서 비교할 수 있지만, 오래된 측후방 관측을 최신 관측으로 취급하면 안 된다. 현재 모든 뷰를 요구하는 런타임에 이런 스케줄이 구현되어 있다고 가정하지 않는다.
6. 8GB 실험은 예를 들어 PyTorch allocator 7GiB 이하와 총 프로세스 GPU 사용량을 함께 관측한다. 4GB 실험은 3GiB allocator부터 비교한다. CUDA context·다른 라이브러리·프레임 버퍼가 별도로 필요하므로 allocator 제한만으로 총 메모리를 보장하지 않는다. 16GB GPU에 8GB 제한을 건 결과는 실제 8GB 장치의 속도가 아니다.

## 지표가 나빠진 후보를 채택하지 않는 절차

선정할 핵심 지표와 검증 manifest·라벨 해시, resize 정책, 임계값 선택 규칙, 클래스 매핑, 장치·정밀도를 먼저 고정한다. 알려진 지표를 하나의 평균으로 합쳐 악화를 가리지 않는다. 새로운 detector 과제처럼 기존 기준 결과가 없으면 **미평가**로 기록하고, 기준선 0점에서 개선했다고 표현하지 않는다.

- 기존 BDD/CamVid/KITTI의 도로 IoU와 비도로→도로 오인을 각각 비교한다. 평가 해상도·GT 처리 방식이 바뀌면 기존 수치와 직접 비교하지 않고 기준 모델도 같은 규약으로 다시 측정한다.
- 설정과 같은 거리 경계 **`[0, 20, 40, 60, 80, 120, 160]m`**를 사용해 0–20 / 20–40 / 40–60 / 60–80 / 80–120 / 120–160m를 구분한다. 객체 크기, 클래스, 카메라 역할, 날씨·야간별 재현율과 고정 오검출 수준의 ROC/PR을 비교한다. 거리 정답이 없는 자료로 거리별 성능을 꾸미지 않으며, 해당 구간의 표본이 없으면 미평가로 보고한다.
- 작은 장애물의 객체 단위 누락, 연속 누락 시간, 도로 오분류 픽셀, 경계 오차를 함께 기록한다. 이미 개발에 사용한 RoadObstacle21/RoadAnomaly21 공개 라벨은 회귀 검사용이며 새 독립 시험 자료로 부르지 않는다.
- 반복 프레임 누수 없이 주행·장소·날짜 단위로 분리한다. 설정과 같은 주 속도 구간 **75–85km/h**에서 실제 속도·촬영 조건이 확인되는 자료와 그 외 자료를 나누며, 정지 영상에 속도 숫자만 붙여 80km/h 시험으로 취급하지 않는다.
- 정해 둔 지표 중 하나라도 악화하면 후보를 보존하되 기준 체크포인트를 교체하지 않는다. 표본 수가 부족하거나 조건이 달라 우열이 불명확하면 보류한다. 반복 측정과 불확실성 구간도 보고하며, 유한한 시험으로 모든 미래 상황의 무회귀를 보증하지 않는다.
- 인식 점수뿐 아니라 전체 지연·메모리·입력 신선도도 별도 통과 조건으로 둔다. 4GB fallback이 이 조건을 만족하지 못하면 해상도를 계속 낮춰 통과시킨 것으로 처리하지 않는다.

## 현재 모델의 위치

현재 TinyUNet 192×320 입력은 도로/비도로 학습 기준선이다. 새 joint 모델의 기본 128×224 입력과 3×5 pooled tokens는 보정·시간·다중 영상 결합 코드의 연구 기준선이며 작은 원거리 객체 보존을 검증한 표현이 아니다. 기본 미래 시각 0.5–2.5초는 80km/h 일정 속도에서 약 11.1–55.6m의 이동에 해당할 뿐, 그 범위의 충돌 검증이나 관측 범위를 뜻하지 않는다.

따라서 위 후보의 검출·분할·추적·거리 검증 결과가 준비되기 전까지 `models_validated_for_control=false`, 8뷰 연구용 물리 출력 차단을 유지한다. 본 문서는 어떤 체크포인트도 자동으로 배포하거나 차량 제어에 연결하지 않는다.
