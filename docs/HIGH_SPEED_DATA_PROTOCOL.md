# 시속 80km 인식·판단 실험의 데이터와 검증 설계

> **과거 실험·연구/인터페이스 참고 문서.** 아래 수치와 진행 표현은 문서 작성 당시의 범위입니다. 현재 완료 결과와 취소/미검증 항목은 [RESULTS](RESULTS.md), 재현 절차는 [REPRODUCIBILITY](REPRODUCIBILITY.md), 운용 한계는 [LIMITATIONS](LIMITATIONS.md)를 우선 확인하십시오. 예제 명령은 설치 시 실행되지 않으며 학습·다운로드·서비스·제어의 새 실행을 뜻하지 않습니다. 로컬 경로는 이 공개본에서 프로젝트 상대 예제로 바꿨습니다.

검토일: 2026-10-21. 이 문서는 공개 자료 조사와 로컬 메타데이터 점검 결과, 앞으로 실행할 실험 설계를 구분한다. 여기서 신규 데이터를 다운로드하거나 CARLA·실차를 실행하지 않았다. 현재 프로젝트의 모델에 80km/h 운행 성능이나 무사고 성능을 인정하는 문서가 아니다.

## 현재 데이터로 확인한 범위

`datasets\virtual_kitti2\metadata`의 5개 장면에서 `clone`, `fog`, `morning`, `overcast`, `rain`, `sunset` 6개 변형을 조사했다. Camera0의 연속한 모든 위치 차이를 **가정한** 0.1초로 나누었으며, stride로 선택한 학습 앵커에만 한정하지 않았다. 원본 장면을 공유하는 날씨 변형은 독립 주행으로 세면 안 된다.

| 항목 | 로컬 계산 결과 |
|---|---:|
| 조사한 연속 위치 구간 | 12,726개 |
| 전체 최대 속도 | 16.870959m/s = **60.735453km/h** |
| 최대값 위치 | Scene18 / clone / frame 1 |
| 75~85km/h 구간 | **0개** |
| 실제 촬영 간격·노출 타임스탬프 검증 | 안 됨 |

| 장면 | 연속 구간 수, 6변형 합계 | 가정한 간격에서의 최대 km/h |
|---|---:|---:|
| Scene01 | 2,676 | 45.0254 |
| Scene02 | 1,392 | 47.2815 |
| Scene06 | 1,614 | 36.6860 |
| Scene18 | 2,028 | 60.7355 |
| Scene20 | 5,016 | 59.0486 |

계산은 `world_to_camera` 행렬의 역행렬에서 Camera0의 월드 위치를 얻고 `norm(position[t] - position[t-1]) / 0.1`을 적용했다. 따라서 위 수치는 **명시된 시간 가정 아래의 메타데이터 감사 결과**다. 실제 80km/h 장면이 확인된 결과가 아니다. 기존 stride 5 학습 앵커만 조사했을 때의 최대 16.660246m/s와 구분한다.

동영상을 빠르게 재생하거나 프레임을 건너뛰면 처리량·프레임 누락 스트레스 시험에는 사용할 수 있다. 원본 촬영의 실제 속도, 노출, 모션 블러, 다른 차량과의 상호작용, 제동 물리를 80km/h 조건으로 바꾸지는 못한다. CARLA도 시뮬레이션 시간과 실제 계산 시간을 구분한다. [CARLA 시간 설정](https://carla.readthedocs.io/en/latest/adv_synchrony_timestep/)

## 추가 데이터의 우선순위와 확인할 내용

아래의 “미확인”은 해당 속도가 없다는 의미가 아니라, 실제 속도·시각을 조사해 개수와 독립 주행 수를 집계하지 않았다는 의미다. 고속도로라는 설명이나 다중 카메라 개수로 80km/h 표본의 존재를 대신 확인하지 않는다.

| 데이터 | 공식적으로 확인되는 영상·속도·시간 정보 | 접근과 규모 | 이 프로젝트의 80km/h 근거 |

comma2k19의 CAN 속도는 m/s이며 처리 로그의 시간은 장치 부팅 기준 초다. 영상의 `frame_times`와 동일 시간축을 확인해 맞추고, `frame_gps_times`와 혼용하지 않는다. 1분 segment가 달라도 같은 원본 route이면 같은 분할에 둔다. Windows에서는 공식 자료가 경로의 `|` 문자 문제와 변환 도구를 설명하므로, 경로 변환 전후의 원본 route ID를 별도 보존해야 한다. 소프트웨어의 MIT LICENSE를 외부 데이터 재배포 허가로 확대해 해석하지 않는다. [comma2k19 공식 README](https://github.com/commaai/comma2k19/blob/master/README.md), [공식 코드 LICENSE](https://github.com/commaai/comma2k19/blob/master/LICENSE)

Argoverse 2는 영상과 LiDAR의 수집 시점 관계가 설명되어 있지만, 모든 카메라가 같은 노출 시각이라는 가정으로 묶지 않는다. 각 카메라의 실제 타임스탬프와 보정값을 이용한다. 이미지가 없는 Argoverse 2 Lidar나 객체 궤적 위주의 Motion Forecasting을 Sensor 영상 데이터의 대체재로 선택하지 않는다. [Argoverse 2 공식 설명·다운로드](https://www.argoverse.org/av2.html), [공식 시각별 위치 로더](https://github.com/argoverse/av2-api/blob/main/src/av2/utils/io.py)

BDD100K의 현재 정지영상은 동영상의 특정 시점에서 추출한 자료다. 정지영상 인식 성능과 시간 정렬한 고속 주행 성능은 별도로 평가해야 한다. [BDD100K 공식 다운로드 설명](https://github.com/bdd100k/bdd100k/blob/master/doc/source/download.rst)

nuScenes CAN expansion은 실험적 데이터임을 명시한다. `vehicle_monitor.vehicle_speed`는 km/h이고, 예제에서 3.6으로 나눠 m/s로 바꾼다. 일부 메시지의 시간은 측정시각 대신 수신시각이므로 동일한 정밀도의 근거로 취급하지 않는다. [CAN 공식 튜토리얼](https://www.nuscenes.org/tutorials/can_bus_tutorial.html), [CAN 메시지 명세](https://github.com/nutonomy/nuscenes-devkit/blob/master/python-sdk/nuscenes/can_bus/README.md)

nuScenes의 촬영 주파수와 주석 keyframe 주파수는 다르다. 실제 프레임 시간차는 일정하지 않을 수 있으므로 12Hz라는 명목값으로 타임스탬프를 덮어쓰지 않는다. [nuScenes 논문](https://arxiv.org/abs/1903.11027), [공식 담당자의 카메라 시간 설명](https://forum.nuscenes.org/t/camera-sampling-rate/415)

Waymo의 서로 다른 세 데이터 상품을 구별해야 한다. End-to-End의 과거 궤적은 4Hz이며 그 사실이 모든 이미지의 노출 주파수라는 뜻은 아니다. 공개 자료 사용 자체로 실제 차량 성능을 검증했다고 해석할 수도 없다. [Waymo 공식 구성 설명](https://waymo.com/open/about/), [공식 접근·이용조건](https://waymo.com/open/terms/)

## 실제 속도 구간을 만드는 규칙

다음은 이 프로젝트에서 사용할 **실험 설계 제안**이다. 공개 데이터가 이미 이 조건을 충족한다는 주장이 아니다.

1. 먼저 영상이 아닌 속도·위치·시간 메타데이터를 읽어 장면별 속도 분포를 만든다. `speed_source`, 원본 단위, clock domain, 측정시각 또는 수신시각 여부, 보간 방법, 시각 정렬 오차를 기록한다. 센서 속도와 위치 차분 속도를 교차 확인하되 불일치를 숨기는 평균을 만들지 않는다.
2. 주 평가 구간은 **사건 시작 또는 평가 앵커의 실측 자차 속도 75~85km/h**, 목표값은 80km/h = 22.222222m/s다. “80 명령” 또는 영상 파일명만으로 합격시키지 않는다. 감속 사건이 시작된 뒤 75km/h 미만으로 내려갔다는 이유로 해당 사건을 제외하지 않는다.
3. 보조 구간은 0~30, 30~50, 50~75, 85 초과로 나누되 경계가 중복되지 않게 구현한다. 속도 구간별 프레임 수뿐 아니라 독립 route/drive 수, 시간·거리, 날씨, 차량 종류, 위험 사건 수를 보고한다. 속도 정보가 없으면 `unknown`으로 남긴다.
4. 현재 `configs/high_speed_80kmh_experiment.json`의 프레임·속도 시각 정렬 허용 오차는 **50ms**다. 20ms는 향후 비교할 수 있는 더 엄격한 선택 조건이며 현재 기본값이 아니다. 어느 값도 안전 인증 기준은 아니다. 누락·중복·역행 시각, 긴 보간 구간, 서로 다른 시계가 섞인 자료를 유효 학습·평가 자료로 세지 않고 원인과 개수를 남긴다. 아래 추적 감사 도구는 정렬 오차가 큰 유효 형식의 행을 삭제하지 않고 실패 건수에 포함한다.
5. 모델 입력의 현재 속도·회전률은 현재 및 과거 측정에서만 만든다. 미래 위치·속도와 양방향으로 평활한 궤적은 정답 작성에 쓸 수 있어도, 인과적 실시간 입력으로 위장해서는 안 된다. 오프라인 최적화된 pose의 한계도 기록한다.
6. 원본 주행 전체로 train/validation/test를 나눈다. 한 route의 인접 segment, 같은 장면의 날씨 변형, 좌우 카메라, 해상도 변경본은 함께 묶는다. 시험 자료로 설정·임계값을 고르지 않는다.

레코드에는 최소한 `origin_id`, `segment_id`, `camera_id`, `image_timestamp_s`, `speed_timestamp_s`, `speed_mps`, `speed_source`, `clock_domain`, `alignment_error_s`, `calibration_id`, `weather`, `ego_speed_bin`, 원본 파일 해시를 남긴다. 원본 데이터에서 모르는 날씨나 노출 시각을 추측해서 채우지 않는다.

## CARLA에서 만들 고속 실험

아래 수치는 **시뮬레이션 설정 후보**이며 실차 주행 명령이 아니다. CARLA 버전·지도·차량 모델·물리 파라미터·센서 blueprint·랜덤 seed를 고정해 저장한다. `latest` 문서는 배포판에 없는 개발 기능을 포함할 수 있으므로 실제 설치 버전의 API와 속성을 확인한다. [CARLA Python API](https://carla.readthedocs.io/en/latest/python_api/)

| 항목 | 초기 실험 제안 | 검증·기록 |
|---|---|---|
| 월드 시간 | 동기 모드, `fixed_delta_seconds=1/60` | 실제 각 snapshot의 frame·timestamp와 dt 기록 |
| 물리 세부 시간 | substepping 사용, 최대 substep `1/240`, 최대 substep 수 4 | 월드 1 step을 물리 최대 4 substep으로 처리하는 조건을 확인 |
| 카메라 시각 | 기본 `sensor_tick=1/30`, 정확히 월드 2 step마다 촬영 | callback 도착순 대신 측정 frame·timestamp로 대응. 모든 카메라의 누락과 시간차 기록. world frame ID를 trace frame ID로 쓰면 `frame_id_stride=2` 명시 |
| 자차 속도 | 22.222222m/s 목표를 둔 물리 기반 주행 | 같은 snapshot의 속도 벡터 크기를 측정하여 75~85km/h 진입 확인. target velocity와 실현 속도를 구별 |
| 이미지 | 실제 후보 렌즈의 시야각·해상도·장착 위치를 별도 명세 | K·외부변환·왜곡을 저장. 8대라는 개수만 고정한 가상 보정을 실제 보정이라고 표시하지 않음 |
| 노출·블러 | 수동/자동 노출, shutter 설정, motion blur 강도·최대 왜곡 비교 | 설정값과 렌더 결과를 함께 점검. 렌더 효과를 실센서 노출·rolling shutter 검증으로 간주하지 않음 |
| 날씨와 노면 | 맑음·야간·역광·안개·비를 렌더 조건으로 분리 | 젖은 외관과 실제 마찰·제동 물리를 별도 파라미터로 관리 |

공식 문서에 따라 동기 고정 시간과 물리 substep 조건을 맞춘다. GPU 카메라 데이터는 지연되어 도착할 수 있으므로 frame ID로 수집해야 한다. 느린 렌더링이 시뮬레이션을 기다리게 하는 상황과, 실제 탑재 컴퓨터가 마감 시간을 놓치는 상황을 따로 시험한다. [CARLA 동기·시간·물리 설정](https://carla.readthedocs.io/en/latest/adv_synchrony_timestep/)

카메라 문서는 `sensor_tick`, 시야각, 해상도, shutter, 노출, motion blur 속성을 제공한다. 설정 가능한 렌더 옵션이 실제 센서의 모든 현상을 정확히 재현한다는 의미는 아니다. [CARLA 센서 명세](https://carla.readthedocs.io/en/latest/ref_sensors/)

CARLA의 WeatherParameters는 RGB 외관에 영향을 주며 차량 물리를 자동으로 바꾸지 않는다고 명시되어 있다. 따라서 비가 오는 영상만 생성하고 젖은 노면의 제동을 검증했다고 보고하면 안 된다. 물리 마찰 변경과 제동 응답은 별도 실험으로 기록한다. 측정 속도는 같은 tick의 actor snapshot에서 얻는 것이 적절하다. [CARLA 날씨·ActorSnapshot API](https://carla.readthedocs.io/en/latest/python_api/)

## 시나리오 행렬

처음에는 각 행을 낮은 속도의 코드 검사로 실행한 뒤, **시뮬레이션에서만** 실제 측정 속도 75~85km/h 구간으로 확대한다. 아래 사건·범위는 연구용 제안이며 충돌 없이 통과할 수 있다는 보증이 아니다. 사건의 타이밍, 다른 차의 상대 속도, 장애물 크기·거리, 가림 비율은 모두 저장한다.

| ID | 사건 | 변화시키는 조건 | 우선 측정값 |
|---|---|---|---|
| lead_constant | 앞차 일정 속도·간격 유지 | 상대 속도, 1·2·3초 초기 차간 시간, 차량 크기 | 거리·상대 속도 오차, 추적 끊김 |
| stopped_vehicle | 정지 차량·정체 꼬리 | 직선·곡선·언덕 정상, 가림 뒤 등장 | 최초 안정 검출 거리, 미검출 연속시간 |
| lead_hard_brake | 앞차 감속·급제동 | 초기 차간 시간, 앞차 감속도, brake-light 가림 | 최초 위험 인지 시각, 감속 요청 지연, 최소 여유거리 |
| cut_in | 좌우 차량의 끼어들기 | 상대 속도, 횡속도, 간격, 측면 가림 | 측면에서 전방으로 객체 ID 연속성, 상대 운동 오차 |
| pedestrian_crossing | 보행자 또는 자전거 횡단 | 가림·등장 시점·크기·이동 방향 | 노출 후 첫 검출, 거리별 recall, 충돌/근접 사건 |
| small_debris | 낮은 물체·낙하물 | 높이·너비·대비, 입력에서 차지하는 픽셀 수 | 장애물을 도로로 오인한 비율, 발견 가능 거리 |
| curve_lane_boundary | 곡선·차선 합류·공사 경계 | 곡률·경사·차선 희미함·가드레일 | 경계 이탈, 궤적 횡오차, 원거리 인식 누락 |
| partial_occlusion | 다른 차량·시설물에 부분적으로 가린 물체 | 가림 비율, 가림 해제 시점, 물체 크기·거리 | 가려진 동안의 추적, 등장 후 첫 검출, 거짓 확신 |
| camera_failure | 카메라 가림·끊김·정지 영상·시간차 | 카메라별 발생 시점과 지속시간 | 고장 검출 시간, 오래된 입력 사용 시간, 동작 제한 여부 |

위 9개 ID는 현재 설정의 `scenario_families`와 같다. 교차 조합은 `ego_speed_bin × scenario_id × condition × fault × seed`로 기록한다. condition은 `day_dry`, `night_dry`, `rain_wet`, `backlight`, `fog`이며, fault는 `none`, `frame_drop`, `frozen_frame`, `timestamp_skew`, `camera_blackout`, `gpu_throttle`, `queue_backlog`다. 노출·블러·가림 정도도 부가 파라미터로 남긴다. 설정에는 조합별 최소 독립 seed 30개와 목표 속도 유지 5초를 제안했지만 아직 실행한 수량은 아니다. 처음에는 명시한 작은 조합을 모두 실행하고, 사건별 실패 원인이 확인되면 인접 조건을 확대한다. 여러 seed의 유사 장면을 독립된 실제 도로 검증 거리로 환산하지 않는다. 같은 지도·배치·사건 seed의 변형은 같은 분할 그룹에 둔다.

## 결과를 보고할 때의 기준

- **인식:** 차량·보행자·자전거·낮은 물체를 분리하고 설정의 거리 경계 **`0, 20, 40, 60, 80, 120, 160m`**를 사용한다. 구간은 `0–20 / 20–40 / 40–60 / 60–80 / 80–120 / 120–160m`이며 경계 중복 없이 집계한다. 160m 초과는 범위 밖 자료로 따로 남긴다. 거리와 모델 입력의 물체 크기별 recall·precision·미검출 연속시간을 보고하며, 도로 IoU만으로 충돌 회피 능력을 평가하지 않는다.
- **거리·운동:** 정답이 있는 경우 거리·상대 속도 오차와 불확실성 보정을 보고한다. 정답이 없는 공개 영상에서는 오차를 “미평가”로 남긴다. simulator depth/위치 정답은 평가에 쓰되 camera-only 모델 입력에 몰래 넣지 않는다.
- **판단·제어:** 순수 녹화영상 재생의 추정 궤적 오차와, 시뮬레이터에서 행동이 다음 관측을 바꾸는 시험의 충돌·최소거리·차선 이탈·불필요한 감속을 구별한다. 선택한 사례를 통과한 결과를 무사고 확률 100%로 표현하지 않는다.
- **시간:** 센서 노출 또는 측정 시각에서 판단·제어 출력까지의 전체 지연을 p50/p95/p99/p99.9·최댓값과 함께 측정한다. GPU 연산 시간만 기록하지 않는다. 80km/h에서는 20ms 동안 약 0.44m, 50ms 동안 1.11m, 100ms 동안 2.22m, 200ms 동안 4.44m를 진행한다. 이는 `거리=속도×시간`으로 계산한 값이다.
- **범위:** 현재 joint policy의 미래 2.5초는 80km/h 등속에서 약 55.6m에 해당한다. 필요한 인지·계획 범위와 실제 제동 응답을 먼저 정한 뒤 horizon·해상도·시야각을 검토한다. 기존 horizon이나 VRAM 목표에 맞추기 위해 요구 범위를 임의로 줄이지 않는다.
- **재현성:** 모델·데이터 manifest·카메라 보정의 해시, 원본 drive 분할, 다운로드·준비 버전, 실제 측정 속도 분포, 시뮬레이터 설정과 실패 사례 목록을 저장한다. 아직 실차 보정·지연·제동·운행환경 검증이 없으므로 `models_validated_for_control=false`를 유지한다.

실행 순서는 **속도·시각 메타데이터 조사 → 실제 75~85km/h 공개 영상 평가 집합 구성 → 독립한 저속·고속 시뮬레이션 사건 검증 → 탑재 장치에서 동시 카메라·지연 측정**이다. 이 문서는 실차 고속 실험을 시작하거나 모터·브레이크에 출력을 연결하는 작업을 수행하지 않는다.

## 기록된 지연 추적을 검사하는 도구

`scripts/audit_high_speed_trace.py`는 이미 수집한 JSONL 추적을 검사한다. 카메라·차량·시뮬레이터에 접속하지 않는다.

```text
python scripts/audit_high_speed_trace.py --trace TRACE.jsonl --metadata METADATA.json --spec configs/high_speed_80kmh_experiment.json --output NEW_REPORT.json
```

메타데이터에는 `schema_version=1`, `measurement_kind`, `clock_domain`, `clock_sync_verified=true`, `clock_uncertainty_ms`, `speed_source`, `hardware_id`, `diagnostic`을 명시한다. 측정 종류는 실제 하드웨어의 노출→명령, 시뮬레이터 시간의 노출→명령, 재생 입력→명령을 구별한다. 속도 출처로 명목 명령값은 받지 않는다. 이 선언 자체로 측정 출처의 진위를 증명하지는 않는다.

한 감사 파일은 하나의 `hardware_id`와 연속적인 `clock_domain`을 전제로 한다. 서로 다른 `unit_id`의 노출 시각 범위가 겹치거나 경계를 공유하면 입력을 거부한다. 동일한 카메라·처리 시각 행을 `unit_id` 또는 `frame_id`만 바꾸어 복제해도 거부한다. 시간 범위가 분리된 주행만 합산하며, 재부팅 등으로 시계가 초기화되었다면 별도 감사 파일·보고서로 분리한다. 세션 사이 공백을 관측 시간이나 촬영률 분모로 더하지 않는다.

각 행은 원본 주행 `unit_id`, 증가하는 `frame_id`, 역할별 최신 노출 시각 8개인 `camera_times_s`, `received_s`, `inference_start_s`, `inference_end_s`, `decision_s`, `command_s`, `speed_mps`, `speed_timestamp_s`를 갖는다. `brake_onset_s`는 **선택 필드**이며 실제 제동 사건의 반응 시작을 측정했을 때 해당 명령과 연결해 넣는다. 모든 프레임에 임의 제동 시각을 채우지 않는다. 시뮬레이션에서는 시뮬레이터 제동 사건임을 measurement kind로 구분하고, 이를 실제 브레이크 측정으로 부르지 않는다. 모델에 쓰는 더 오래된 history 프레임은 `camera_times_s`에 섞지 않는다.

검사는 8개 최신 프레임 중 **가장 오래된 측정 시각부터 명령까지**를 기본 지연으로 사용한다. 현재 기본 전방 촬영 목표는 **30Hz**다. 15/20/60Hz는 설정에 포함된 비교 조건이며, 해당 조건을 실험할 때는 별도 설정·보고서로 구분한다. 카메라 간 최신 시각차 한도는 **10ms**, 속도와 최신 영상의 시각 정렬 한도는 **50ms**, 선언한 시계 불확실성 한도는 **1ms**다. 시간차·정렬 불일치·재사용된 노출 시각·누락된 frame ID를 실패 항목으로 센다.

기본 촬영률은 실제 기록에서도 확인한다. **최소 실효 촬영률은 29Hz**이며 각 주행과 전체 집합·고속 집합에서 모두 만족해야 한다. 실효 촬영률은 주행 내 양의 관측 시각 간격 수를 그 간격의 총시간으로 나눈 값이다. 긴 간격도 분모에 포함하므로 느린 구간을 삭제해 촬영률을 높이지 않는다. 고속 촬영률은 연속한 양쪽 표본의 속도가 모두 75~85km/h이고 시각 정렬이 유효할 때 계산한다. 충분한 간격이 없으면 촬영률 근거가 부족한 것으로 처리한다. 별도의 `1.5 / 30Hz` 간격 검사를 통과하는 20Hz 기록도 이 실효 촬영률 기준에는 실패한다.

현재 지연 목표는 **p99.9 ≤100ms, 최댓값 ≤150ms, 100ms 초과 비율 0**이다. 전체 자료와 **실제 속도가 75~85km/h인 자료 각각에 대해 최소 30,000표본과 관측 지속시간 1,800초를 모두** 요구한다. 고속 표본 수·지속시간은 속도 시각 정렬이 유효한 기록으로 확인한다. 이 요구는 전체 및 고속 집합 기준이며, 각 원본 주행의 표본·지속시간도 별도로 보고한다. 정상적인 30Hz 기록 1,800초는 약 54,000프레임이므로 30,000표본만 채웠다고 지속시간 조건까지 충족하는 것은 아니다. 세션 간 공백이나 관측하지 못한 구간은 지속시간에 더하지 않는다.

제동 반응 근거는 **고유 사건 최소 100개, 이 중 정렬이 유효한 75~85km/h 제동 사건 최소 100개**를 요구한다. 고유 사건은 `(unit_id, brake_onset_s)`로 세며 같은 사건을 여러 행에 반복 기재해 수량을 늘리지 않는다. 반복된 사건의 지연은 연결된 행 중 가장 긴 노출→제동 시작 지연으로 평가한다. **모든 사건의 가장 오래된 최신 카메라 노출→제동 시작은 300ms 이하여야 한다.** 사건이 없거나 부족하거나 한 사건이라도 한도를 넘으면 근거 부족·목표 미달로 남긴다. 제동 percentile은 관측한 표본의 경험적 보간값이며, **100개 사건만으로 p99.9 꼬리 지연이나 안전 실패 확률을 검증한 것은 아니다.** 기록 생산자가 연결한 명령·제동 사건의 진위도 이 도구가 독립적으로 증명하지 않는다.

합성 fixture는 `diagnostic=true`로 표시한다. 재생 결과를 노출→작동 지연으로 바꾸어 부르지 않으며, 시뮬레이터 시간의 지연을 실제 컴퓨터 처리 시간으로 간주하지 않는다. 영상 픽셀이 없는 추적 파일만으로는 새 타임스탬프를 붙여 전송한 검은 화면이나 정지 영상을 검출할 수 없다. 이런 고장은 별도의 실제 영상 검사가 필요하다. 모든 결과는 연구용이고 `deployment_approved=false`, `physical_validation_completed=false`다. 이 도구는 실제 장치의 진위, 검출 정확도, 사고 회피 능력을 인증하지 않는다.
