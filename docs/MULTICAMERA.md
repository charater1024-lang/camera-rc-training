# 네 방향 카메라 구성과 판단 범위

> **과거 실험·연구/인터페이스 참고 문서.** 아래 수치와 진행 표현은 문서 작성 당시의 범위입니다. 현재 완료 결과와 취소/미검증 항목은 [RESULTS](RESULTS.md), 재현 절차는 [REPRODUCIBILITY](REPRODUCIBILITY.md), 운용 한계는 [LIMITATIONS](LIMITATIONS.md)를 우선 확인하십시오. 예제 명령은 설치 시 실행되지 않으며 학습·다운로드·서비스·제어의 새 실행을 뜻하지 않습니다. 로컬 경로는 이 공개본에서 프로젝트 상대 예제로 바꿨습니다.

이 프로젝트의 확장 목표는 **전방·후방·좌측·우측 4대**입니다. 현재는 장비를 연결하지 않은 개발 준비 단계입니다. 첫 연결과 성능 측정은 한 대로 시작하고, MSI 장비를 확보하면 네 방향을 점차 추가합니다. 카메라 네 대가 특정 차체의 모든 사각지대를 없애거나 충돌을 방지한다는 보장은 아닙니다.

| 카메라 수 | 적합한 단계 | 한계 |
|---|---|---|
| 전방 1대 | 모델·보정·USB·제어 연결 검증 | 측면·후방을 볼 수 없고 회전 중 새로 차지할 영역이 안 보이면 정지 |
| 전·후·좌·우 4대 | 이번 저속 주변 관측 확장 목표 | 실제 화각·위치·차체 가림·근접 사각지대 측정 필요 |
| 6대 이상 | 앞 모서리나 좁은 화각의 빈 공간 보완이 필요한 경우 | GTX 1650 4GB의 계산·USB·전력 여유를 다시 측정해야 함 |

네 대라는 수는 이 프로젝트의 초기 설계 판단입니다. 예를 들어 [nuScenes](https://www.nuscenes.org/)는 6개 카메라와 다른 센서를 포함하지만, 그 수나 데이터를 사용하는 것만으로 우리 차량의 주변 인식이 완성되지는 않습니다. 실제 보정·배치가 우선입니다.

## 배치와 필요한 보정

전후좌우 카메라는 이웃 방향과 시야가 겹치고 차체 가까운 지면이 보이도록 검토합니다. 카메라 간 정확한 수평 화각과 설치 높이는 차체 크기·곡률·필요 관측 거리로 정합니다. 횡방향 차량 끝과 코너, 회전 시 뒤쪽이 차지하는 공간도 촬영해야 합니다. 선택한 렌즈·장착 위치가 결정되기 전 숫자만으로 관측 범위를 확정하지 않습니다.

각 카메라의 렌즈 보정과 지면 투영을 따로 측정하고 **공통 원점 = 후륜 축 중심, x=차량 전방, y=차량 좌측, 단위=m**를 사용합니다. 후방 영상이라고 x축을 뒤집지 않습니다. 다중 카메라 보정의 기본 개념은 [OpenCV 보정 안내](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html)를 참고하세요. 현재 런타임 렌즈 보정은 OpenCV의 일반 pinhole 왜곡 모델입니다. 전용 fisheye/omnidirectional 모델이 필요한 렌즈를 동일한 계수로 처리할 수 있다고 가정하지 않습니다.

`calibrate-ground`로 카메라마다 대응점과 독립 검증점을 측정해 다음 파일을 만듭니다.

- `configs/calibration_front.json`
- `configs/calibration_rear.json`
- `configs/calibration_left.json`
- `configs/calibration_right.json`

형식은 기존 [운용 안내](RUNTIME.md)를 따릅니다. `coordinate_origin=rear_axle_center`가 필수이며 보정 도구가 이를 기록합니다. 후방 `supported_range`는 음수 x 범위를 지원합니다. 측면은 기존 좌우 대칭 `max_abs_lateral_m` 대신 `min_lateral_m`, `max_lateral_m`로 한쪽 범위를 지정할 수 있습니다. 보정 범위는 실제 측정점의 볼록 껍질 안에 있어야 합니다. 가상의 보정 행렬은 진단용으로만 생성합니다.

## 구현한 입력·판단 연결

```text
네 방향 카메라의 최신 영상
  → 모든 필수 방향이 새 영상인지, 수신 시각 차이가 제한 안인지 확인
  → 각 방향 렌즈 보정
  → 하나의 경량 모델로 방향별 순차 추론
  → 공통 차량 좌표에서 관측 결합 + 모든 방향의 장애물 투영
  → 차량 전체가 이동하며 차지하는 공간 검사
  → 기한이 유효한 경로만 독립 제어 루프로 전달
```

`source.kind=multicamera`는 각 카메라의 최신 프레임 하나만 보관합니다. 한 방향의 이전 프레임을 재사용해 새 묶음으로 내보내지 않습니다. `max_skew_s=0.04`는 초기 **호스트 수신 시각 차이** 제한입니다. 이것이 노출 동기화를 뜻하지 않습니다. 카메라의 내부 버퍼·노출 차이는 실제 측정하거나 지원하는 하드웨어 동기화 방식으로 확인해야 합니다.

오래된 프레임, 누락, 카메라 읽기 실패, 기한 초과에는 정지합니다. 프레임 묶음의 시각과 경로 유효기간은 **가장 오래된 방향**을 기준으로 계산합니다. 모든 필수 카메라가 새롭고 시간차가 허용되는 경우에만 묶음을 처리합니다. 물리 출력에는 기존 조건 외에도 촬영·전송 지연 검증 후 `source.capture_timing_validated=true`가 필요합니다. 이 설정은 운영자의 확인값이며 자동 인증이 아닙니다.

경로의 새 이동 영역은 적어도 한 카메라에 관측되어야 합니다. 겹치는 관측에서 하나라도 도로가 아니거나 확신이 낮으면 다른 방향의 높은 도로 확률로 덮어쓰지 않습니다. 현재 차체가 이미 차지한 영역만 제외하며 새롭게 차지할 사각지대는 통과시키지 않습니다. 객체 탐지가 켜져 있으면 모든 방향의 지면상 장애물을 합칩니다. 캡처 장치 중복도 검사하고 파일·URL을 실시간 카메라로 지정하는 입력은 거부합니다.

현재 계획·제어는 **전진 전용**입니다. 후방 카메라를 추가했어도 후진·자동 주차를 구현한 것은 아닙니다. 뒤쪽 관측은 전진 회전 중 차체 후방의 이동 영역을 검사하는 데도 쓰입니다.

## GTX 1650 4GB용 초기 설정

`configs/runtime_msi_4cam_dryrun.json`을 준비했습니다. 실제 파일과 장치 경로를 채우기 전에는 실행되지 않습니다.

| 항목 | 초기 후보 |
|---|---|
| 카메라 | 640×360, 카메라별 30fps 요청 |
| 영상 형식 | MJPG 요청, 실제 장치 지원 여부 확인 |
| 모델 | 공유 TinyUNet width16, 192×320 입력, batch1 순차 추론 |
| 정밀도 | MSI FP32 비교 기준, FP16은 별도 측정 |
| 완전한 네 방향 묶음 목표 | 10Hz, 달성 보장 아님 |
| 제어 목표 | 독립 50Hz, OS 실시간 보장 아님 |
| 기한 | 처리 150ms, 가장 오래된 관측부터 경로 만료 200ms |
| 출력 | dry-run |

카메라 30fps는 읽기 요청이고 네 방향 판단 10Hz는 별도 목표입니다. USB 대역폭이 부족하면 최신 영상이 제때 도착하지 않습니다. 예를 들어 비압축 YUY2 2바이트/픽셀을 가정하면 4×640×360×30×2 = 약 **55.3MB/s**이며 USB 프로토콜 부하는 제외한 값입니다. 같은 허브에 네 대를 꽂았다고 각각 충분한 대역폭이 생기지 않습니다. `MJPG` 설정은 장치가 거절할 수 있으며 실제 포맷·프레임 간격·CPU 디코딩 부하를 확인해야 합니다. 동기화 문제를 처리율 숫자만으로 판단하지 않습니다.

기본은 분할만 실행하고 탐지는 선택 사항입니다. 실제 장애물 분류에 필요한 탐지를 추가하면 연산 비용이 늘므로 다시 측정합니다. 한 모델을 공유해도 네 방향의 추론 시간은 발생합니다. 10Hz를 못 맞추면 먼저 모델·해상도·연산 병목을 검토하며, 정지 오류를 없애려고 시간 제한만 늘리지 않습니다. 여러 센서나 더 높은 성능의 하드웨어가 필요한지 판단할 수 있는 기준을 측정으로 만듭니다.

## 현재 PC에서 가능한 확인

```powershell
.\.venv\Scripts\python.exe -m camera_rc drive-fixture --multiview --device cuda --output runs/four_camera_fixture_new
.\.venv\Scripts\python.exe -m camera_rc drive-benchmark --config runs/four_camera_fixture_new/runtime.json --output runs/four_camera_benchmark_new.json --frames 100 --warmup 10
.\.venv\Scripts\python.exe scripts/run_headless.py --config runs/four_camera_fixture_new/runtime.json --dry-run --max-frames 100
```

벤치마크의 `frames`는 네 방향 전체 묶음 수입니다. 모델 인스턴스 수, 방향별 입력 크기, 묶음 지연, 가용 RAM, GPU 메모리와 목표 주기 충족 여부를 보고합니다. 합성 영상은 코드·자원 진단이며 실제 시각 인식 성능이나 MSI 처리 속도의 근거가 아닙니다.

기록 영상 입력은 `source.kind=multireplay`로 사용합니다. 각 줄은 아래 형태이며 경로는 JSONL 기준입니다. `offset_s`는 0 이하인 상대 수신 시각으로 진단에 사용합니다. 모든 설정된 방향이 있어야 하고 물리 출력은 금지됩니다.

```jsonl
{"views":{"front":{"image":"front.jpg","offset_s":0},"left":{"image":"left.jpg","offset_s":-0.01},"right":{"image":"right.jpg","offset_s":-0.02},"rear":{"image":"rear.jpg","offset_s":-0.01}},"speed_mps":0.1,"yaw_rate_rps":0.0}
```

## 충돌 회피를 위한 학습과 남은 검증

네 방향의 정확한 마스크와 장애물 정답, 다양한 조명·바닥·가려짐·근접 상황이 필요합니다. 동일 주행을 train/val로 쪼개지 않고 방향별 검증 성능을 따로 확인합니다. [네 방향 학습 안내](MULTIVIEW_TRAINING.md)에 준비 도구와 단계별 설정이 있습니다.

현재 모델은 표면 분할을 학습하고, 계획·제어는 규칙과 차량 기하를 사용합니다. **충돌 회피 자체를 학습한 통합 모델은 아닙니다.** 도로 표면인 픽셀과 실제 빈 공간은 다릅니다. 지금의 정적 평지 투영으로 턱·경사·공중 돌출물·가려진 물체·빠르게 들어오는 보행자의 3차원 위치와 미래 충돌까지 해결하지 못합니다. 시간축 추적·접근 속도/TTC·거리 인식, 캘리브레이션 변화, 제동 지연, 센서 이상 상황의 추가 검증은 남아 있습니다. 데이터셋 수나 시뮬레이션 통과만으로 실제 차량의 무충돌을 주장하지 않습니다.
