# USB 시리얼 차량 제어 규약 v2

> **과거 실험·연구/인터페이스 참고 문서.** 아래 수치와 진행 표현은 문서 작성 당시의 범위입니다. 현재 완료 결과와 취소/미검증 항목은 [RESULTS](RESULTS.md), 재현 절차는 [REPRODUCIBILITY](REPRODUCIBILITY.md), 운용 한계는 [LIMITATIONS](LIMITATIONS.md)를 우선 확인하십시오. 예제 명령은 설치 시 실행되지 않으며 학습·다운로드·서비스·제어의 새 실행을 뜻하지 않습니다. 로컬 경로는 이 공개본에서 프로젝트 상대 예제로 바꿨습니다.

v2는 센서 **측정 표본의 시각과 순번**을 필수로 추가한 호환성 변경입니다. PC와 MCU 양쪽을 함께 갱신해야 합니다. v1 명령·상태는 거절하며, v2라고 표시했어도 센서 필드가 없으면 PC가 추진을 허용하지 않습니다. 구형 패킷의 수신 시각을 측정 시각으로 대신 채우는 호환 모드는 없습니다.

PC 런타임은 `SerialTransport`로 MCU와 통신합니다. 기본값은 **230400 baud, 8N1**, UTF-8 JSON 한 줄에 LF 한 개입니다. 기본 50 Hz 제어에서 양방향 메시지 길이를 고려한 값입니다. 보드가 낮은 baud만 지원하면 제어 주기와 메시지 크기를 함께 조정하고 실제 왕복 지연을 측정하십시오. `230400`은 MCU에서도 동일하게 설정해야 합니다.

현재 구현된 것은 PC 드라이버, 제어기, MCU 동작의 실행 가능한 참조 모델과 테스트입니다. **실제 보드 핀·ESC·서보·엔코더 펌웨어는 보드가 정해진 후 구현해야 합니다.** `src/camera_rc/driving/mcu_reference.py`는 Python으로 규약을 검증하는 참조 모델이며 MCU에 바로 업로드하는 펌웨어가 아닙니다. 이를 PC에서 실행하는 것으로 MCU 독립 감시 기능을 대체할 수 없습니다.

## 단위와 물리 입력

- 차체 좌표는 앞쪽 `+x`, 왼쪽 `+y`입니다. 거리 m, 속도 m/s, 조향·yaw rad, yaw rate rad/s를 사용합니다.
- `steering_rad > 0`이면 바퀴가 왼쪽으로 돌아갑니다. 실제 조향 링크/서보 매핑에서 부호를 확인해야 합니다.
- `throttle`은 0~1의 전진 출력이며 현재 구현은 후진 주행을 지원하지 않습니다. PC와 MCU 양쪽 기본 상한은 0.3입니다.
- `brake`는 0~1의 검증된 감속·정지 요구입니다. `brake > 0`이면 throttle은 반드시 0입니다. **brake=1을 ESC의 역방향 PWM으로 단순 변환하면 안 됩니다.** 사용 ESC의 중립·제동·후진 전환 동작에 맞게 매핑하고 제동이 가능한지 검증해야 합니다. 제동이 없는 하드웨어에서 정지 거리를 보장할 수 없습니다.
- 속도는 엔코더/검증된 속도 센서의 실제 측정값이어야 합니다. PWM이나 목표 속도를 측정 속도로 돌려보내면 폐루프 속도 제어가 성립하지 않습니다. yaw rate는 IMU 또는 검증된 운동학 측정값을 사용합니다.
- `armed`는 MCU의 **물리적 활성화 스위치** 및 MCU 안전 상태에서 결정합니다. PC에서 자동 arm하거나 메시지로 물리 스위치를 우회하지 않습니다.
- 비상 정지는 MCU의 물리 입력으로 처리하고 가능하면 구동 전원 차단 회로에도 연결합니다. USB/PC 응답을 기다리지 않습니다.

## PC → MCU 명령

```json
{"v":2,"type":"command","session":"0123456789abcdef0123456789abcdef","seq":1,"host_ms":123456789,"ttl_ms":150,"enabled":false,"steering_rad":0.0,"throttle":0.0,"brake":1.0,"target_speed_mps":0.0,"reason":"startup"}
```

| 필드 | 의미 |
|---|---|
| `session` | PC 연결마다 새로 만드는 128-bit 난수, 32자리 소문자 hex. 이전 연결의 명령을 구별합니다. |
| `seq` | 세션 내 1부터 엄격히 증가하는 정수. 재전송·역순 명령은 거절합니다. |
| `host_ms` | PC의 monotonic 시각(ms). 시스템 날짜가 아닙니다. |
| `ttl_ms` | 명령의 최대 유효 기간. 기본 150ms. 수신 지연을 제외한 남은 기간만 MCU watchdog에 적용합니다. |
| `enabled` | 출력 허용 요청. 실제 허용에는 MCU의 물리 arm, estop, calibration, watchdog 조건도 필요합니다. |
| `target_speed_mps` | 계획된 속도. PC의 PI 제어기가 실제 측정 속도로 throttle/brake를 산출합니다. MCU는 별도 상한을 적용합니다. |
| `reason` | 진단용 문자열. 동작을 해석하는 명령으로 사용하지 않습니다. |

첫 명령과 새로운 세션을 시작하는 명령은 항상 `enabled=false, throttle=0, brake=1`이어야 합니다. 단순 포트 열기는 arm이나 움직임을 발생시키지 않아야 합니다. PC의 `SerialTransport`도 새 연결에서 일치하는 telemetry를 받기 전에는 활성 명령을 STOP으로 바꿉니다.

PC는 `calibration_confirmed: true`를 명시하고 신선한 상태에서 물리 arm/estop 조건이 확인되어야 활성 명령을 전송합니다. 기본값은 false입니다. MCU 측에서도 별도 calibration 확인과 상한을 적용합니다. 이 설정은 학습 모델의 품질을 보증하는 설정이 아닙니다.

## MCU → PC 상태

```json
{"v":2,"type":"state","session":"0123456789abcdef0123456789abcdef","telemetry_seq":1,"ack_seq":1,"host_ms":123456789,"mcu_ms":10020,"sensor_seq":42,"sensor_ms":10010,"speed_mps":0.0,"yaw_rate_rps":0.0,"armed":false,"estop":false}
```

- `ack_seq`와 `host_ms`는 MCU가 **마지막으로 유효하게 처리한 명령**의 값입니다. 거절한 명령을 ACK해서는 안 됩니다.
- `telemetry_seq`는 세션 내에서 상태를 보낼 때마다 엄격히 증가합니다. 이는 메시지 순번이며 새 측정 표본이 생겼다는 뜻이 아닙니다.
- `sensor_seq`는 속도와 yaw rate **둘 다 새로 취득·검증된 표본 묶음**에만 증가시킵니다. 스위치를 다시 읽거나, 같은 센서값을 다시 전달하거나, telemetry를 전송할 때 증가시키면 안 됩니다. 숫자가 같은 실제 새 측정값은 허용합니다. 표본 순번을 증가시키는 기준은 값의 변화가 아닌 실제 취득 완료입니다.
- `sensor_ms`는 그 표본 묶음 중 **가장 오래된 측정의 MCU monotonic 취득 시각(ms)**입니다. 센서가 서로 다른 속도로 갱신되면 오래된 쪽을 기준으로 합니다. 새 묶음의 순번과 시각은 둘 다 증가해야 합니다. 반복 표본은 순번·취득 시각·속도·yaw rate를 모두 유지해야 합니다. 타이머나 전송 시각을 취득 시각으로 대신 넣지 않습니다.
- `mcu_ms`는 상태 패킷 생성 당시의 MCU monotonic 시각입니다. `mcu_ms - sensor_ms`가 MCU에서 이미 지난 표본 나이입니다. PC 시계와 같은 기준일 필요는 없지만, 같은 MCU 시계에서 나온 값이어야 합니다. 표본 나이가 음수거나 시각·순번이 역행하면 거절합니다.
- 첫 측정 전 참조 MCU는 `sensor_seq=0, sensor_ms=null`로 미취득 상태를 명시하며 계속 STOP입니다. PC는 이 패킷을 운용 가능한 차량 상태로 받아들이지 않습니다. 알 수 없는 측정값이나 취득 시각을 추정해 활성 상태로 만들지 않습니다.
- PC는 세션 불일치, 재사용된 telemetry 순번, 과거로 돌아간 ACK, 아직 보내지 않은 미래 ACK, host_ms 불일치, NaN/무한대, 잘못된 물리 상태 필드를 거절합니다.
- PC 기본 상태 제한은 `state_timeout_s=0.25`, 센서 표본 제한은 별도 `sensor_timeout_s=0.25`입니다. 수신 시각뿐 아니라 ACK된 원래 명령의 전송 시각으로도 오래된 상태를 판정합니다. 센서 나이에는 `mcu_ms - sensor_ms`와 ACK 명령의 전체 왕복 경과 시간을 더합니다. 실제 반환 구간보다 길게 잡는 보수적 상한이며, 두 시계를 동기화했다고 가정하지 않습니다. 이 상한은 ACK 처리 뒤 상태 패킷을 생성한다는 규약에 의존합니다.
- PC는 같은 센서 표본을 반복해서 받아도 기존 표본 시각을 새 수신 시각으로 바꾸지 않습니다. 제어기에 전달하는 시각도 패킷 수신 시각 대신 위 지연을 반영한 보수적 표본 시각입니다. 한 번 유효한 측정을 받은 뒤 센서 나이·순번·시각 검사가 실패하면 해당 PC 연결은 정지 상태를 유지하고, 새 PC 세션과 MCU의 물리 재무장을 요구합니다. 부팅 중 첫 표본이 아직 없는 상태는 새 유효 측정을 기다립니다.
- 상태가 없거나 오래되면 PC는 STOP을 요청합니다. 메시지는 기본 2048 bytes/줄, 수신 버퍼는 8192 bytes로 제한하며 과다 입력도 실패 처리합니다.
- MCU 재부팅으로 telemetry 순번이 초기화된 경우 이전 세션을 계속 사용하지 않습니다. PC 런타임을 재연결하여 새 세션과 물리 재활성화를 수행합니다.

## MCU에 반드시 이식할 상태 기계

`McuSafetyReference`는 다음 규칙을 구현하며 `tests/test_mcu_reference.py`에서 검사합니다.

1. 부팅·리셋·포트 재연결 시 throttle=0, brake=1 상태로 시작합니다. USB DTR 때문에 MCU가 리셋되는 보드도 같은 규칙을 지킵니다.
2. 새 세션은 안전한 STOP으로만 수락하고 물리 스위치를 OFF→ON으로 다시 조작해야 arm이 가능하도록 합니다.
3. 스위치 OFF, estop, 잘못된 명령, 순서가 뒤바뀐 명령, 만료된 명령은 즉시 정지시킵니다. estop과 watchdog 오류는 고정된 오류 상태로 유지하고 물리 OFF→ON 전환 후에만 해제합니다.
4. **PC와 독립적으로 MCU 타이머에서 watchdog을 검사합니다.** 참조 주기는 5ms입니다. 마지막 유효 명령의 남은 TTL이 지나면 throttle=0, brake=1을 적용합니다. USB 분리, PC 멈춤, 모델 추론 정지, 송신 오류가 있어도 작동해야 합니다.
5. 세션의 첫 안전한 STOP으로 두 monotonic 시계의 offset을 잡고 이후 host_ms 경과량과 MCU 경과량을 비교합니다. 증가하는 seq라도 전송 큐에서 오래 지연된 명령은 TTL을 초과하면 거절합니다. 지연이 TTL 이내라도 watchdog에는 `ttl_ms - 수신 지연`만 적용하여 유효 기간이 늘어나지 않게 합니다. 참조 모델은 PC 시각이 50ms 넘게 앞선 경우도 거절합니다. 장시간 시계 드리프트는 보수적인 정지를 유발할 수 있으므로 보드 이식 시 측정·검증해야 합니다.
6. 잘못된 명령은 watchdog을 갱신하지 않습니다. 실제 servo/ESC 출력은 항상 이 상태 기계의 최종 출력에서만 갱신합니다.
7. C/C++ 이식에서는 millis() overflow에 안전한 차이 계산을 사용합니다. JSON parser 용량, 숫자 범위, 입력 버퍼 상한, 정수 증가/랩어라운드 처리도 검증합니다. 허용 범위를 넘어서는 세션은 STOP 후 재연결합니다.
8. **센서 표본 watchdog을 명령 watchdog과 독립적으로 검사합니다.** 참조 기본 `sensor_timeout_ms=250`에서 마지막 표본 취득 시각으로부터 250ms 이상 지나면 정지 오류를 고정합니다. 정상 명령과 telemetry가 계속 오가더라도 센서 취득이 멈추면 이 오류가 발생해야 합니다. 같은 표본을 `set_inputs()`로 반복 전달해도 만료 시각은 늘어나지 않습니다. 신선한 측정만 복구하거나 명령을 재전송하는 것으로 오류가 풀리지 않으며, 신선한 측정·유효 명령이 확보된 후 물리 스위치를 OFF→ON으로 바꾸어야 합니다.

250ms와 150ms 등은 참조 시험의 초기 제한값이며 실제 차체에 안전하다고 입증된 수치가 아닙니다. 센서 취득 주기, 통신 지연, 독립 타이머 지연, 실제 제동 거리를 측정하여 MCU와 PC의 제한을 정해야 합니다. 물리 arm/estop 스위치는 센서 작업이나 USB 처리 때문에 읽기가 지연되지 않는 경로로 처리하고, 센서 fault와 함께 추진을 차단해야 합니다. 센서 드라이버가 고장 난 값을 새 표본이라고 거짓으로 표시하는 오류까지 timestamp 규약만으로 검증할 수는 없습니다. 드라이버의 취득 완료·하드웨어 상태와 센서 고장 진단도 별도로 검증해야 합니다.

참조 API:

```python
from camera_rc.driving.mcu_reference import McuSafetyReference

mcu = McuSafetyReference(calibration_confirmed=False, sensor_timeout_ms=250)
# 아래 호출은 실제 MCU 펌웨어로 이식해야 합니다.
mcu.set_inputs(physical_armed=False, estop=True,
               speed_mps=measured_speed, yaw_rate_rps=measured_yaw_rate,
               sensor_seq=completed_sample_bundle_sequence,
               sensor_ms=oldest_actual_acquisition_ms,
               now_ms=mcu_monotonic_ms)
mcu.receive_line(received_complete_line, mcu_monotonic_ms)
actuator_command = mcu.tick(mcu_monotonic_ms)  # 통신이 없어도 주기적으로 호출
status = mcu.telemetry(mcu_monotonic_ms)
```

## 보드 연결 전후 확인

핀 번호나 임의의 서보 펄스를 이 저장소에서 추정하지 않습니다. 선택한 MCU 펌웨어에서 실제 wheelbase, 좌/우 조향 각도-펄스 매핑, 조향 한계, ESC 중립/정지/제동, encoder 방향·ticks/revolution·바퀴 둘레, IMU 축, arm/estop 입력의 전기적 기본 상태를 설정하십시오. 외부 출력 회로는 MCU 리셋 중에도 구동하지 않아야 합니다.

최초 확인은 구동 바퀴를 지면에서 띄운 상태에서 수행합니다. 이후 정해진 저속 코스에서 실제 제동 거리와 지연을 측정합니다. USB 분리, PC 프로세스 강제 종료, 카메라 제거, 추론 정지, MCU reset, encoder 오류, 물리 estop 각각에 대해 정지 및 재활성화 조건을 확인해야 합니다. **정상 명령을 계속 보내면서 센서 취득만 중단하는 경우**, 반복 표본을 새 패킷에 담는 경우, 센서 복구 후 물리 재무장 없이 출력이 재개되지 않는 경우도 각각 확인합니다. Python 테스트는 이 하드웨어 검증을 대신하지 않으며 실제 무사고를 보장하지 않습니다.

## 제어기

`Controller`는 경로의 전방 lookahead 점에 pure pursuit를 적용합니다. 조향 각도와 각속도를 제한하고, 목표 속도에 가속·감속 제한을 적용한 후 **측정 속도 기반 PI**로 throttle/brake를 계산합니다. 적분은 출력 포화 시 누적을 막습니다. 기본 wheelbase 0.26m, 최고 속도 0.6m/s 등은 예시 값이며 실제 차체에 맞게 설정해야 합니다. 안전 정지는 정상 감속 제한보다 우선합니다. STOP 시에는 바퀴 각도를 유지하여 갑작스러운 조향 복귀를 피합니다.

기본 `stop_to_align=true`에서는 원하는 조향과 현재 명령의 차이가 `alignment_tolerance_rad=0.04`보다 크면 먼저 현재 조향을 유지하며 제동합니다. 측정 속도가 `alignment_speed_mps=0.03` 이하가 된 뒤에는 제동을 유지한 채 조향 명령을 제한 속도로 변경하고, 정렬된 이후에 전진 출력을 재개합니다. 급격한 곡률 전환 중 계획한 원호와 실제 명령의 경로가 달라지는 것을 줄이기 위한 보수적인 동작입니다. **현재 규약에는 실제 바퀴 조향각 피드백이 없으므로 여기서 정렬은 명령값 기준입니다.** 서보 응답·유격·마찰·정착 시간과 정지 중 조향의 기계적 부담은 실제 하드웨어에서 검증해야 합니다. 계획한 경로를 실제로 따른다는 보증은 아닙니다.

유효 경로·신선한 측정·물리 활성화 중 하나라도 없으면 STOP입니다. camera/perception/plan의 지연 제한은 상위 runtime에서 추가로 검사합니다. 모든 수치는 초기 저속 실험 값이며, 실제 차량의 허용 속도·정지 성능을 보증하는 수치가 아닙니다.
