작성일: 2026-10-21. 작업 위치: `.`.

**현재 모델은 80km/h 운행에 사용할 수 있다고 검증되지 않았다.** 이 작업에서 만든 것은 모델 비교안, 계산 도구, 평가 조건, 측정 로그 검사 도구다. 80km/h 영상을 새로 학습했거나 CARLA·실차 시험을 완료한 결과가 아니다. 차량 출력은 기존 `dry_run`과 `models_validated_for_control=false`를 유지한다.

사용자가 요청한 “모든 부분 개선”은 사전에 고정한 인식·거리·추적·경로·제어·지연 지표를 모두 비교하는 방식으로 다룬다. 한 지표만 좋아져도 채택하지 않는다. 관측하지 않은 상황까지 성능 향상이나 무사고를 보장할 수는 없다.

## 현재 결과를 다시 판단하면

기존 동일 평가 자료에서 BDD 도로 IoU는 **67.28 → 71.20%**, CamVid는 **58.25 → 60.58%**, KITTI Road는 **67.08 → 77.24%**로 개선됐다. 그러나 RoadObstacle21 공개 30장에서는 정답 장애물 픽셀을 도로로 잘못 판단한 비율이 **10.13 → 18.55%**로 악화됐다. 이는 픽셀 오류율이며 충돌 확률이 아니다. 비도로를 도로로 예측한 비율도 세 도로 자료 모두 악화했다.

따라서 이 추가 학습 모델은 **전반적인 개선 후보로 채택하지 않는다**. 점수의 근거는 `runs/additional_data_evaluation_v1/comparison.json`이며, 새 평가와 같은 지표·단위인 것처럼 합치지 않는다. 기존 대용량 학습 큐가 만드는 체크포인트도 추가 연구 후보일 뿐이다.

현재 Virtual KITTI 2의 5장면·6변형을 조사한 결과, 프레임 간격을 0.1초로 가정했을 때 최대 속도는 약 **60.74km/h**, 75~85km/h 구간은 **0개**였다. 실제 촬영 시각이 검증된 값은 아니다. 현재 BDD 정지영상 역시 속도·노출 시각이 연결된 고속 주행 시험 자료가 아니다. 영상을 빨리 재생하는 것은 원래 장면을 80km/h 촬영 조건으로 바꾸지 않는다. 상세 근거: [데이터 검증 계획](HIGH_SPEED_DATA_PROTOCOL.md).

현재 예약된 joint 학습은 Virtual KITTI 2의 실제 제공 전방2뷰를 사용한다. 8뷰 입력 코드는 합성 입력으로 동작을 확인한 단계이며 실제8카메라 배치에서 학습·검증된 모델이 아니다.

## 우선 비교할 모델

후보 범위를 **YOLO26n/s/m/l/x 전체**로 확장했다. 아래 n/s 구성은 초기 비교 기준이다. 학습은 현재 RTX3080 Laptop16GB·RAM32GB를 활용하고, **4GB·8GB 제한은 배포 비교에 적용**한다. 큰 모델도 실제 메모리·전체 지연·정확도 조건을 충족하면 직접 배포 후보가 될 수 있다. 세부 실험 명세는 `configs/model_scale_experiment.json`, 계산과 근거는 [모델 비교 문서](MODEL_CANDIDATES_80KMH.md)에 있다.

| 용도 | 전용 VRAM 8GB 후보 | 기존 MSI 4GB 비교군 |
|---|---|---|
| 전방 객체 검출 | **YOLO26s**, 입력960과640 비교 | **YOLO26n**, 입력640 |
| 도로·주행 경계 | **PIDNet-S**, 전방512×1024부터 | PIDNet-S, 384×768과512×1024 비교 |
| 시간 추적 | ByteTrack, 카메라별 2D 추적 | 동일 |
| 분할 구조 비교 | YOLO26s + SegFormer-B0 | 우선순위 낮음 |
| 큰 모델 직접 배포 비교 | YOLO26m/l/x, 입력640·960 | 같은 모델을 배제하지 않고 실측 비교 |
| 거리·상대 운동 | 보정된 전방 스테레오/다중 시점, 차속·IMU와 결합 후 실제 거리 정답으로 검증 | 동일한 검증 필요 |

모델을 8개로 복제하지 않고 검출기와 분할기 인스턴스를 공유한다. 카메라 간 융합에는 보정·노출 시각·자차 운동과 불확실성이 추가로 필요하다. ByteTrack만으로 3D 거리나 카메라 간 동일 객체 연결이 해결되지 않는다. PIDNet의 semantic 경계와 차선 표시 인식도 다르므로 차선 표시용 라벨·head를 따로 평가한다.

YOLO26s를 우선 비교하는 이유는 작은 n 모델보다 검출 용량을 늘리고 원거리 입력 해상도 상승의 효과를 측정하기 위해서다. PIDNet-S는 경계 정보를 다루는 실시간 분할 후보로 선택했다. 공식 COCO·Cityscapes 성적과 다른 GPU에서의 FPS를 우리 차량 성능으로 환산하지 않는다. [YOLO26 공식 설명](https://docs.ultralytics.com/models/yolo26/), [PIDNet 공식 저장소](https://github.com/XuJiacong/PIDNet).

**이는 검증 전 후보 선정이며 설치·학습·통합이 끝난 구성이 아니다.** 실제 GPU 종류와 전력 제한에 따라 속도 차이가 크므로 “8GB”만으로 실행 속도를 정할 수 없다. RAM16GB도 운영체제·8영상 디코딩·버퍼·모델을 모두 포함해 측정해야 한다. 호스트 RAM 여유, 프레임 대기열, 최대 GPU 메모리를 같이 기록하고 부족하면 RAM32GB 또는 다른 GPU를 비교한다. 해상도를 낮춰 메모리만 맞추고 작은 장애물 재현율이 나빠지는 구성은 채택하지 않는다. [모델 상세 비교](MODEL_CANDIDATES_80KMH.md).

## 80km/h에서 필요한 시간과 관측 범위

80km/h는 **22.22m/s**다. 100ms 동안 **2.22m**, 300ms 동안 **6.67m**를 이동한다. 30Hz 촬영 간격에도 약 **0.74m**를 이동한다.

정지 장애물·직선·일정 감속을 가정한 계산은 `정지 필요 거리 = 속도 × 반응 시간 + 속도² / (2 × 감속도) + 여유 거리`다. 아래의 반응0.3초와 여유10m, 감속도는 **실측이 아닌 실험 가정**이다.

| 가정한 감속도 | 반응·제동·여유를 합한 거리 |
|---|---:|
| 7m/s² | 약 **51.94m** |
| 4m/s² | 약 **78.40m** |
| 3m/s² | 약 **98.97m** |

노면, 타이어, 경사, 제동 상승 시간, 움직이는 상대 차량은 별도 변수다. 100ms 인식 지연만 만족한다고 정지 거리가 확보되지는 않는다. 현재 joint 모델의 2.5초 예측 구간은 일정한80km/h에서 약55.6m에 해당하므로, 고속 연구에는 **5~6초 예측과 120~160m 관측 구간**을 추가 비교한다. 실제 미래 정답·보정·시야가 준비돼야 하며, 기존 저속 제어기의 속도 상한만 올리지 않는다.

카메라의 광학적 한계도 있다. 정사각 픽셀 pinhole 근사에서 폭960·수평 화각90°라면 80m 앞 높이15cm 물체는 약 **0.9픽셀**이다. 모델을 크게 바꾸는 것만으로 안정적인 인식을 기대할 수 없다. 전방 원거리용 좁은 화각과 주변 광각의 겹침, 원본 해상도, 노출·블러를 비교하고 원거리 작은 물체를 실제 거리 구간별로 평가한다. 이 투영 계산은 검출률이 아니다. [OpenCV 투영 모델](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html).

## 지연 측정 규약

`노출 → 수신 → 전처리·복사 → 추론 → 추적·융합·판단 → 제어 명령 → MCU 수신 → 제동 시작`을 하나의 검증된 시간축으로 기록한다. 현재 추가한 trace 검사기는 노출·수신·추론·판단·명령·선택적 제동 시작을 읽는다. MCU ACK와 세부 전처리는 별도 계측 후 로그를 확장해야 한다. 모델만 측정한 FPS와 전체 지연을 혼용하지 않는다.

| 연구용 초기 조건 | 값 |
|---|---:|
| 기본 카메라 촬영 | 30Hz, 8개 최신 영상의 촬영 시각 기록 |
| 실효 촬영 주파수 | 최소29Hz; 20Hz 로그를30Hz 시험으로 통과시키지 않음 |
| 가장 오래된 최신 영상의 노출 → 명령 | p99.9 ≤100ms, 최대 ≤150ms |
| 100ms 마감 초과 비율 | 0을 목표로 측정; 따라서 초기 게이트에서는 단 한 번의 초과도 차단 |
| 카메라 간 최신 노출 시각 차이 | ≤10ms |
| 영상과 속도 측정 시각 정렬 | ≤50ms |
| 시계 동기 불확실성 | ≤1ms |
| 측정 분량 | 전체와 실측75~85km/h 구간 각각 ≥30,000표본 **및** ≥1,800초 |
| 노출 → 제동 시작 비교 목표 | p99.9 ≤300ms, 제동 사건을 따로 수집·계측 |
| trace 제동 검사 | 고유 제동 사건 전체·고속 각각 최소100개, 관측된 모든 노출→제동 지연≤300ms |

모두 실험을 위한 임시 목표이며 안전 기준이나 검증된 차량 한계가 아니다. 30Hz·30분이면 약54,000프레임이며, 연속 프레임은 독립 안전 시험이 아니다. 제동100건은 계측 부족을 막는 최소값일 뿐 p99.9 꼬리 위험을 입증하는 분량이 아니다. 작은 표본의 percentile은 기술 통계로만 읽고 반복·추가 사건을 수집한다. 열이 오른 상태에서 CPU/GPU 전력·클럭·온도, 디코딩·USB 부하, RAM/VRAM, 프레임 유실·재사용을 기록한다. 입력의 과거 이력과 현재 사용 중인 오래된 최신 프레임을 구분한다.

제동 시작 시각은 실제 사건의 명령과 연결해 측정해야 한다. 영상 재생 수신 시각은 실제 노출 시각이 아니며, 시뮬레이터 시간은 호스트 계산 시간과 다르다. 예를 들어 녹화된80km/h 영상을 멈춘 장치에 재생하는 시험은 계산·수신 지연 실험이지 실제80km/h 제동 시험이 아니다. 3개 평가 게이트에서 이 서로 다른 증거를 한 자료처럼 합치지 않는다.

trace의 시계·장치 정보는 수집기가 선언한 값을 검사하며 실제 하드웨어를 인증하지 않는다. 같은 시각의 기록을 주행 ID만 바꿔 중복 계산하지 못하게 차단한다. 하나의 연속 시계를 전제로 하므로 장치 재부팅 등 시계가 초기화된 기록은 별도 검사한다. 새 타임스탬프가 붙은 검은 영상·정지 영상은 픽셀 검사가 추가로 필요하다.

## 실행 순서와 학습 비교

1. **기준 고정:** 데이터 출처·원본 주행 ID·분할 해시, 입력·정답·거리 구간·각 지표의 분모·임계값을 먼저 고정한다. 원본 route, 인접 영상 조각, 좌우 영상, 날씨 변형은 함께 분할한다. 장애물이 없는 표본의 재현율을 임의로1로 채우지 않는다.
2. **인식 재학습:** 도로/비도로 이진 분할만으로 물체가 없다고 판단하지 않는다. 객체·보행자·작은 미등록 장애물, 도로·경계·차선 표시를 분리 평가한다. 기존 BDD 등 자료를 유지하면서 장애물 hard-negative와 어려운 날씨 자료를 균형 있게 섞고, 실제 고속 자료를 마지막 단계에 추가한다. 공개 장애물 평가 이미지를 학습에 사용했다면 회귀 검사 자료로만 유지하고 새로운 독립 시험 주행을 확보한다.
3. **공정한 비교:** 같은 연산량의 기존 데이터 전용 학습군, 추가 데이터 학습군, 모델 구조 변경군을 분리한다. 학습 seed3개 이상, 같은 고정 시험 자료로 비교한다. 새 구조의 큰 입력·더 많은 학습 시간과 추가 데이터 효과를 하나로 주장하지 않는다. FP16/TensorRT/INT8도 각각 정확도·전체 지연을 다시 평가한다.
4. **고속 실영상 검사:** 계정 없이 받을 수 있는 후보인 comma2k19의 속도·시각 메타데이터부터 확인한다. 실제75~85km/h 구간·독립 주행 수를 집계한 뒤 필요한 영상을 취득한다. 약100GB라는 전체 규모만으로 다운로드를 시작하거나 고속 자료가 충분하다고 가정하지 않는다. 전방 한 시야이므로 별도의 주변 카메라 자료도 필요하다. [comma2k19 공식 자료](https://github.com/commaai/comma2k19/blob/master/README.md).
5. **폐루프 시뮬레이션:** CARLA에 카메라·차량 물리를 명시하고 실제 달성 속도로 사건을 분류한다. 정지 차량, 앞차 급제동, 끼어들기, 보행자, 작은 낙하물, 곡선 경계, 가림, 센서 고장을 시험한다. 지시 속도80만 기록하지 않는다. 위험 사건 후 감속해75 미만이 되더라도 그 사건을 버리지 않는다. 모든 상황에서 멈추기만 하는 모델은 경로 완주 실패·불필요 제동 지표로 차단한다.
6. **탑재 장비·액추에이터 계측:** 실제 MSI 또는 선정한8GB GPU에서 headless 실행과 8카메라 취득을 시험한다. 차량을 구동하지 않는 장비 시험부터 전기적 명령·MCU ACK·기계적 제동 응답을 분리 계측한다. 이 단계만으로 고속 제동 성능을 인정하지 않는다. 고속 실차 시험은 이 작업의 실행 범위가 아니다.

CARLA 설정은 world1/60초, physics substep최대1/240초×4, camera1/30초다. 날씨 외관만 바꾸면 제동 물리가 자동으로 바뀌지 않으므로 마찰·차량 물리를 따로 기록한다. [CARLA 시간 설정](https://carla.readthedocs.io/en/latest/adv_synchrony_timestep/), [CARLA 날씨·물리 API](https://carla.readthedocs.io/en/latest/python_api/).

전체 기본 행렬은 속도7개×사건9개×날씨5개 = **315조건**이며, 조건당seed30개면 **9,450회**다. 고장 강도·기간의 추가 조합은 이 수에 포함되지 않는다. 우선80km/h만의45조건·1,350회부터 시뮬레이션할 계획이다. 현재 생성되는 것은 **미실행 시나리오 목록**이며 CARLA 시나리오 실행기는 아직 구현하지 않았다. 실제 환경에 사건을 만드는 코드·정답·계측 연결이 추가로 필요하다.

## 개선 여부를 판정하는 코드

도메인이 다른 측정을 섞지 않도록 같은 CLI에 다음 세 명세를 각각 넣는다.

| 명세 | 요구하는 측정 |
|---|---|
| `configs/high_speed_perception_gate.json` | 도로IoU·비도로 오인·장애물 오인·차량/보행자/원거리 작은 물체 재현율·오검출·차선 경계·거리·상대 속도·ID 전환 |
| `configs/high_speed_simulation_gate.json` | 궤적ADE/FDE·횡오차·속도오차·jerk·최소 여유거리 개선, 충돌·차선 이탈·불필요 급제동·경로 실패0 |
| `configs/high_speed_timing_gate.json` | 노출→명령 및 노출→제동 지연 개선, 마감 초과·오래된 입력 사용·메모리 부족 없음 |

지표마다 최소30개 원본 주행 단위의 대응 비교를 사용한다. `speed_75_85__rain_wet`처럼 고속과 날씨·사건이 동시에 충족된 조건의 독립 주행 수도 요구한다. 별도의 주간 고속 주행과 저속 우천 주행을 합해 고속 우천을 시험했다고 처리하지 않는다. 합성 날씨 복제나 반복 재생을 독립 주행으로 늘리지 않는다. 시뮬레이터에서는 원본 시나리오·seed와 그 변형을 같은 독립 단위로 묶고 `evidence_domain=simulated`로 보고한다. 경로 실패에는 시간 초과·미완주·지속 정지를 포함한다.

개선 방향으로의 평균 변화와 다중 비교 보정한 bootstrap 하한이 모두0보다 커야 한다. 관측된 어느 주행 단위라도 악화하면 차단한다. 충돌·마감 초과처럼 이미0인 지표는 더 낮출 수 없으므로0을 유지해야 한다. 표본·지표·정답이 없으면0점이나합격으로 채우지 않고 `blocked`로 남긴다. 기준 모델이 해당 기능을 제공하지 못하면 먼저 측정 가능한 기준 모델을 구현해야 한다.

이 강한 조건은 많은 후보를 보류할 수 있다. 시험 결과를 본 뒤 조건을 몰래 낮추지 않는다. 전체 평균뿐 아니라 각 거리·카메라·날씨의 구간별 결과도 따로 보고한다. 현재 게이트의 주행 단위 요약만으로 세부 구간 전체를 검증했다는 주장은 하지 않는다. 세 게이트의 결과가 있어도 배포 승인은 항상false이며, 시뮬레이션·진단 자료는 `diagnostic_checks_passed`까지만 반환한다.

## 도구 실행

프로젝트 루트의 가상환경에서 실행한다. 출력 경로는 기존 결과를 덮어쓰지 않는 새 경로여야 한다.

```powershell
.\.venv\Scripts\python.exe -X utf8 -B scripts/design_high_speed_experiment.py --config configs/high_speed_80kmh_experiment.json --output runs/high_speed_design_v1

# 실제로 수집한 JSONL·메타데이터가 있을 때 실행한다.
.\.venv\Scripts\python.exe -X utf8 -B scripts/audit_high_speed_trace.py --trace <측정.jsonl> --metadata <측정정보.json> --spec configs/high_speed_80kmh_experiment.json --output runs/high_speed_trace_v1.json

# 모듈 설명의 schema에 맞춘 원본 주행별 평가 결과가 필요하다.
.\.venv\Scripts\python.exe -X utf8 -B scripts/evaluate_candidate_gate.py --baseline <기준평가.json> --candidate <후보평가.json> --spec configs/high_speed_perception_gate.json --output runs/high_speed_perception_gate_v1.json

# 기존 학습·다른 GPU 부하가 없을 때의 구조 비용 측정: 정확도 측정 아님.
.\.venv\Scripts\python.exe -X utf8 -B scripts/benchmark_detector_candidates.py --model yolo26n --imgsz 640 --views 8 --precision fp16 --device cuda --groups 20 --warmup 3 --gpu-budget-gib 4 --output runs/yolo26n_architecture_cost_v1.json
.\.venv\Scripts\python.exe -X utf8 -B scripts/benchmark_detector_candidates.py --model yolo26s --imgsz 960 --views 8 --precision fp16 --device cuda --groups 20 --warmup 3 --gpu-budget-gib 8 --output runs/yolo26s_architecture_cost_v1.json
.\.venv\Scripts\python.exe -X utf8 -B scripts/benchmark_detector_candidates.py --model yolo26x --imgsz 640 --views 8 --precision fp16 --device cuda --groups 20 --warmup 3 --gpu-budget-gib 4 --output runs/yolo26x_architecture_cost_4gb_v1.json
```

게이트 CLI는 `blocked`일 때도 JSON을 정상 저장하므로 프로세스 종료코드0을 합격으로 해석하면 안 된다. 반드시 JSON의 `status`, `decision`, 각 지표와 누락 사유를 읽는다. 측정 trace를 만드는 카메라·MCU 수집기는 이 작업에 포함되지 않았다. 입력 schema는 각 스크립트와 테스트 예제에 있다.

검출 벤치마크는 설치된 YOLO26 YAML로 **무작위 가중치**를 생성한다. 사전학습 가중치 다운로드나 정확도 측정이 없고, 전처리·카메라·분할·추적·제어 시간도 제외한다. 8GB 메모리 제한을 RTX3080에 적용해도8GB급 다른GPU 성능을 재현하지 않는다. 짧은20회 결과로 p99.9를 주장하지 않는다.

실제 설치된 YOLO26n을 CPU·FP32·640·1뷰에서 실행해 `[1,300,6]` 검출 출력 구조를 확인했다. 설치 버전에서는 융합 전에 검출 head의 `end2end=True`를 명시해야 했으며, 해당 동작을 회귀 테스트로 고정했다. 이 짧은 CPU 실행은 통합 동작 검사일 뿐 정확도·8뷰 GPU 처리량·80km/h 성능 결과가 아니다. 후보의 GPU 단독 측정은 기존 학습이 GPU를 사용 중이어서 이번 작업에서 실행하지 않았다.

최초 완료 범위와 검사는 `runs/high_speed_design_v1/verification.json`, 모델 규모 확장의 추가 검사는 `runs/model_scale_update_v1/verification.json`에서 확인한다. 기존 v1 계산은 당시 설정 해시를 보존한 기록이다. 계산된 거리와 미실행 목록, 코드 테스트 결과를 실제 인식률·반응 시간·무사고 성과로 표현하지 않는다.
